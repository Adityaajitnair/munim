## Step 2: Build in this order

1. **Voice to text.** Write a small script that sends a recorded audio file to Sarvam's speech-to-text. Test 10 to 15 sentences in Hinglish ("Amul ke 50 packet, 1500 ka bill") and note the accuracy and latency. This is your biggest technical risk, so test it first .	
2. **Text to structured JSON.** Add an LLM step with a strict prompt and schema (intent, supplier, item, quantity, total). Validate with Pydantic. Match supplier names against a supplier table, because speech-to-text will often mangle them.
3. **FastAPI core.** Build `POST /voice` (receives audio, returns the parsed order) and `POST /confirm`. Store each order with a status: `PENDING_CONFIRMATION` → `CONFIRMED` → `EXECUTED`. This state machine makes your confirmation safety claim real.
4. **n8n workflow.** Trigger it via webhook when an order is confirmed. Send the WhatsApp message, then call back to FastAPI to mark the order executed. Add one retry path.
5. **Voice confirmation.** Use text-to-speech to read back "50 Amul milk, ₹1,500. Confirm?" (Sarvam has a TTS model; check the docs). Run the "haan" reply back through step 1.
6. **Demo interface.** A simple web page with a mic button (browser audio recording), a live ledger table, a simulated Soundbox, and a mock WhatsApp view. Streamlit is fastest, or plain HTML.

## Step 4: Make your deck's claims true

Your slides mention "420ms latency," "20-second confirmations," and "10+ languages." Once the prototype runs, **measure real numbers** and update the slides. Real measured latency, even if slower, is more credible than an unexplained number. Also mark anything simulated (Paytm API, Soundbox) honestly.

## Biggest risks

- **Hinglish accuracy.** Test early and keep a "didn't catch that, please repeat" fallback.
- **WhatsApp approvals.** Use the sandbox and don't depend on the real API.
- **Time.** Finish the golden path before adding features. Record a backup demo video in case live voice fails on stage.
